## Likely causes
- **Prompt / skill issue:** weak numerical-debugging discipline and poor self-consistency. Root cause supported by repeated syntax regressions (`step_id` 3, 5, 8, 15, 27, 33, 35, 43, 52, 62, 84) and contradictory mathematical claims (`step_id` 22, 69, 74, 90).  
- **Middleware / harness issue:** no termination guard requiring the final artifact to satisfy explicit numeric checks before allowing a success-style final response (`step_id` 89–92).  
- **Not primarily infrastructure failure:** tools generally worked; failures were mostly model-generated code errors. One minor environment limitation appeared (`hexdump` missing at `step_id` 41), but it was not outcome-determining.

## Generic harness fixes
- Require a **final verification gate**: read artifact, compute target metrics, and block completion unless thresholds pass.  
- Add a **syntax/lint retry loop** before long searches, especially after repeated parse failures.  
- Encourage/require **single trusted evaluator functions** reused across all experiments to avoid formula drift and contradictory reasoning.  
- Detect repeated failure pattern (“same syntax bug >N times”) and trigger a reset/replan rather than continued patching.

## Component choice
Primary: **skill**  
Secondary: **middleware**, **prompt**

## Regression risks
- Stronger verification gates may reduce false-successes but increase explicit task failures.  
- More aggressive retry/reset logic may increase runtime/token use on hard numeric tasks.  
- If prompt constraints become too rigid, they could suppress productive exploratory search in tasks where approximation is acceptable.
