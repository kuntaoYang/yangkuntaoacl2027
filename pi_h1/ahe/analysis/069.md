## Outcome
**Failed** for task `069` (`qemu-startup`): final score `0.0`. The rollout never demonstrated a working background QEMU instance reachable at `telnet 127.0.0.1 6665`, and the final attempts still showed connection refusal or QEMU startup failure.

## Evidence-backed patterns

1. **Repeated invalid or incompatible QEMU CLI usage**
   - In **task 069 step 14**, QEMU explicitly rejected `-serial tcp:127.0.0.1:6665,server,target=0,nowait` with `Invalid parameter 'target'`.
   - In **step 15**, QEMU explicitly rejected `-nographic` with `-daemonize`: `-nographic cannot be used with -daemonize`.
   - In **step 16**, another `-serial ... target=...` form was rejected with `Invalid parameter 'target'`.
   - These are proven command-construction errors, not environment flakiness.

2. **The agent did not achieve or verify the required listening service on port 6665**
   - In **steps 10, 11, 14, 15, 16, 18**, direct `/dev/tcp/127.0.0.1/6665` or telnet checks returned `Connection refused`.
   - In **step 17**, the agent got a misleading partial success: QEMU printed `waiting for connection on ... telnet:0.0.0.0:62154,server`, while the agent’s port probe said `Port ready!`; however this output proves QEMU was not listening on the requested port `6665`.
   - Therefore the required endpoint was never established.

3. **Environment/tooling limitations were present but not the main root cause**
   - In **step 4**, `ss` was missing.
   - In **step 6**, `ps` was missing.
   - In **step 7**, `pgrep` was missing.
   - In **step 11**, `pkill` was missing.
   - These are genuine infrastructure/tool availability issues, but they did not prevent success by themselves; QEMU’s own stderr already provided decisive evidence of invalid flags and startup problems in steps 14–18.

## Likely causes
- **Primary cause: model capability / tool-description gap around QEMU CLI syntax.** The rollout repeatedly guessed unsupported `-serial` syntaxes instead of converging on a known-valid invocation, as proven in **steps 14, 15, 16**.
- **Secondary cause: weak readiness-validation strategy.** The agent treated ambiguous signals as progress, e.g. in **step 17** it accepted a probe as “ready” despite QEMU reporting a different port.
- **Infrastructure limitation:** sparse shell utilities (`ss`, `ps`, `pgrep`, `pkill`) in **steps 4, 6, 7, 11** increased friction and likely encouraged brittle ad hoc checks.

## Generic harness fixes
- Provide a **tool description or skill** for common VM-launch patterns (QEMU backgrounding, serial/telnet exposure, readiness checks) so the model does not have to improvise fragile syntax.
- Add middleware that **surfaces and highlights stderr from long-running process launches**; explicit QEMU parse/runtime errors should be treated as hard failures requiring correction.
- Add a generic **port-readiness helper** in the harness so missing `ss`/`ps` utilities do not derail validation.
- Encourage a policy of **verifying exact user-required endpoint/port**, not merely “some listener exists.”

## Component choice
- **Primary:** `skill`  
- **Secondary:** `tool description`, `middleware`  
Not mainly a tool-implementation bug: the shell ran commands and returned accurate stderr.

## Regression risks
- A generic QEMU-launch skill could overfit to one VM configuration and fail on variants needing different display/serial settings.
- More aggressive middleware error handling could incorrectly abort recoverable launches unless tuned to distinguish parse errors from transient boot logs.
- Stronger readiness checks may increase runtime if they wait too long on legitimately slow boots.
