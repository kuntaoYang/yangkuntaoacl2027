## Likely causes

- **Proven observation:** The final payload depended on mechanisms that survive sanitization but are not shown to auto-execute in the target browser (step_ids **54–55**, **63–65**).  
- **Hypothesis:** The model overgeneralized from “payload survives filter” to “payload succeeds,” reflecting a capability gap in browser security semantics and exploit validation, especially for auto-trigger requirements (claims grounded by the repeated selection of `javascript:` URL payloads in step_ids **39**, **42**, **48**, **51**, **54**, **63**).  
- **Proven workflow error:** It misinterpreted a no-op script invocation as a passing test (step_ids **56–57**, **68–71**).

## Generic harness fixes

- Require a **browser-observable success criterion** before declaring completion; mere string-presence checks should not count.
- Add middleware guidance/checklists: “survives sanitizer” vs “executes in target runtime” are distinct gates.
- Detect likely **non-executed test scripts** (e.g., Python file defines tests but exits 0 without running assertions) and warn the agent.
- Encourage use of the specified verifier in a way that actually executes tests, not just the module top-level.

## Primary component choice

- **Middleware**: best fit, because the main failure was incorrect validation and success detection (step_ids **56–57**, **68–71**).  
- Secondary: **Prompt/tool description**, to reinforce end-to-end verification over static reasoning.

## Regression risks

- Overcorrecting toward strict verification may slow agents on simple tasks.  
- Adding heavy browser-validation loops could increase cost/time.  
- Prompting too strongly against heuristic success may reduce initiative in exploratory tasks.
