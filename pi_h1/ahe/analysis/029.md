## Likely causes
- **Model capability limit (minor):** tendency toward over-generalizing validation rules from CWE knowledge to stricter-than-required checks, shown in **steps 12, 19, 26, 30**.  
- **Prompt/skill gap:** insufficient default discipline around “minimal compatible fix” and preserving existing API semantics; regressions only surfaced after running tests (**steps 13, 21–23**).  
- **Tooling friction:** malformed `edit` call in **step 24** indicates weak robustness in structured tool argument generation.

## Generic harness fixes
- Encourage a **“smallest safe patch first”** workflow: after finding the failing area, patch narrowly and run targeted tests before full suite.  
- Add middleware reminders/checklists for **compatibility-sensitive validation changes**: preserve spaces, Unicode, and existing accepted values unless tests/spec prove otherwise.  
- Improve tool-schema assistance or auto-repair for malformed edit payloads to reduce avoidable tool-call failures.  
- Surface **regression deltas** prominently after first test run so the agent pivots faster from overblocking.

## Regression risks
- Tightening header validation can easily block valid inputs such as spaces or Unicode, as seen in **steps 13, 21–23**.  
- Expanding validation from values to names can change API behavior; in this rollout it was necessary for passing tests (**steps 62–64**), but similar changes elsewhere could break compatibility.  
- Overfitting to test feedback remains a risk when security fixes are inferred mainly from suite behavior rather than explicit spec.
